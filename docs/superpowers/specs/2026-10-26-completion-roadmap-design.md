# 완성본 정의와 6주 MVP 단계 설계 (2026-10-26)

- 이 문서는 2026-10-26 사용자와 논의해 정한 **완성본 프로덕트의 정의**와, 남은 5~6주 동안의 **MVP 단계별 구현·검증 계획**이다.
- 상위 기준은 [프로젝트 방향](../../project-direction.md)(Level 0~5)이다. 이 문서는 그 목표를 유지하면서 과목 범위를 넓히고 일정을 정한다.
- 평가 데이터의 사용 원칙은 [평가 데이터셋](../../evaluation-datasets.md)을 따르되, 2-4절의 수정 사항이 우선한다.
- 표기
  - **(결정)**: 사용자가 정한 것.
  - **(제안 채택)**: Claude가 제안하고 사용자가 승인한 것.
  - **(Claude 판단)**: 사용자가 맡겼거나 아직 묻지 않아 Claude가 정한 것. 사용자가 바꿀 수 있다.

## 1. 의도

- 1차 MVP(main `2d634e5`)는 자료구조 선형 구조 11개 개념에서 막힘 흐름 S1~S8이 화면에서 끝까지 동작한다.
- 하지만 두 가지가 없다.
  - 효과를 보여 주는 수치(M1~M3, O1~O3)
  - 이해를 돕는 시각 자료
- 교수님 피드백("그래서 CS 뭘 말하는건데?")은 범위가 너무 넓게 들린다는 지적이다. 6주 범위는 다음 두 가지로 좁힌다.
  - **자료구조로 효과를 증명한다.**
  - **운영체제 한 단원으로 다른 과목에도 적용됨을 보인다.**
- 장기 학습 보조(복습 일정, 기억 추적, 스트릭, 알림)는 넣지 않는다 **(결정)**. 막힌 지점을 이해시키는 학습 자체에 집중한다.
- 한 줄 설명: "자료구조 같은 전공 과목을 공부하다 막혔을 때, 어떤 선수 개념이 빠졌는지 찾아 그것만 메워 주는 학습 도구".

## 2. 완성본 정의 (장기 목표)

6주 안에 전부 만들지 않는다. 이 정의는 3절의 6주 범위를 정하는 기준이고, 6주 뒤에 이어서 만들 방향이다.

### 2-1. 단계별 애니메이션 시각 자료 (결정)

- 흐름을 단계로 쪼개고, 단계마다 상태 변화를 애니메이션으로 보여 준다.
  - 사용자 예시: 변수 선언 → 스택에 공간 할당 → `malloc()` → 힙에 공간 할당 → 주소가 포인터에 저장 → 힙에 값 저장.
  - 이 예시는 스타일 예시이며, 자료구조 개념에 적용한다 **(결정)**.
- 과목마다 애니메이션 종류를 다르게 한다 **(결정)**.
  - 예: 자료구조는 노드·포인터 변화, 운영체제는 시간축 위 프로세스 배치.
- 이전/다음 단계 이동과 단계별 한 줄 설명을 둔다. 막힘 흐름의 보충(S4)과 자유 채팅에서 쓴다 **(제안 채택)**.
- 각 단계의 상태는 코드가 결정적으로 계산한다. 모델은 어떤 장면을 보여 줄지 고르고 설명만 쓴다 **(Claude 판단)**.
  - 이유: 모델이 상태를 지어내면 틀린 그림이 나와도 잡을 방법이 없다.
  - 진단·적용 문항을 결정적으로 채점하는 원칙(project-direction Level 4)과 같은 이유다.

### 2-2. 디펜스 뒤에도 여러 학생이 쓰는 서비스 (결정, 6주 범위 밖)

- 완성본은 여러 학생이 쓰는 서비스다. 필요한 것은 계정, DB 저장, 외부 접속(HTTPS), 동시 사용, 개인정보(동의·보관·삭제), 운영(장애 복구·백업)이다.
- 6주 동안은 공개하지 않고 로컬에서만 진행한다 **(결정)**.
- 유료화하지 않는다 **(결정)**. 그래서 비상업 라이선스 데이터(CS-Bench 등)를 쓸 수 있다.

### 2-3. 전공 5과목과 하나의 연결 지도 (결정)

- 과목: 자료구조, 운영체제, 네트워크, 데이터베이스, 컴퓨터개론.
  - 컴퓨터개론의 범위는 아직 확인하지 않았다. Claude는 2진수·자료 표현, CPU, 메모리 계층으로 해석하고 있다.
- 과목 사이 선수 관계는 하나의 연결 지도로 둔다 **(결정)**.
  - 예: 운영체제의 스케줄링 → 자료구조의 큐·우선순위 큐.
- 완성 시 규모는 개념 약 150~200개, 문항 약 900개 + 루브릭으로 추정한다. 사용자 검수가 병목이다.
- CS-300은 평가 전용으로 유지한다. 어떤 문항 은행·학습 데이터에도 넣지 않는다. 쓰는 범위는 2-4절의 품질 하한 시험을 따른다.

### 2-4. 평가 (결정 + 수정)

- 데이터셋 목록과 번역 원칙은 [평가 데이터셋](../../evaluation-datasets.md)을 따른다.
- 같은 날 AI 엔지니어 검토 결과(Git 밖 `codex/model-evaluation/translation-vs-original.md`)에 따라 아래를 바꾼다 **(제안 채택)**.
  - **M3 최종 근거는 한국어 사람 라벨이다.** 영어 원문(Mohler, SemEval)은 채점 방식을 고치고 비교하는 개발용이다.
  - 지식 문항(CS-Bench)은 원문과 번역을 쌍으로 돌려 언어 차이를 잰다. 번역 결과만으로 품질 하한을 판정하지 않는다.
  - "차이가 작다"는 판단은 미리 정한 허용 폭(예: kappa 차이 ±0.10)과 신뢰구간으로 한다.
  - KMMLU의 CC-BY-ND는 번역본을 공개하는 것만 금지한다. 원문으로 쓰는 결론은 그대로다.
  - 1차 MVP의 서술 채점 kappa 0.92는 Claude가 쓴 가상 답으로 잰 값이다. 상한으로만 읽는다.
- **품질 하한 시험(설명의 사실 정확성)을 공식 데이터셋 중심으로 바꾼다** **(결정)**
  - 근거: AI 엔지니어의 CS-300 검토(Git 밖 `codex/model-evaluation/cs300-reliability.md`).
    - CS-300은 정답 키 오류가 없었다.
    - 하지만 사람 검수를 거치지 않았다.
    - 선택형 240문항은 단서로 풀린다. 오답에만 극단 표현이 있고 긴 보기가 정답이라, 지식 없이 약 86%를 맞힌다.
    - 상위 모델 사이는 가르지 못한다.
  - 한국어 기준: KMMLU Computer-Science(한국 자격시험 기출, 시험용 1,000문항)에서 자료구조·운영체제 문항을 골라 쓴다. 문항마다 수험생 정답률이 있다.
  - 영어 기준: CS-Bench의 자료구조·운영체제 분야를 쓴다.
  - CS-300은 계산·추적 60문항만 남긴다.
    - 풀이를 다시 적기만 한 29개의 정답은 코드 실행으로 재검증한다.
    - 선택형 240문항은 더 쓰지 않는다.
  - 두 공식 데이터셋은 2024년부터 공개돼 있어 최근 모델이 학습 중에 봤을 수 있다.
    - 그래서 점수를 "본 적 있을 수 있는 문항에서의 성능"으로 해석하고, 이 한계를 함께 밝힌다.
    - 보기만 주고 질문은 주지 않는 조건을 함께 돌려, 단서나 암기에 얼마나 기대는지 수치로 남긴다.
  - 원본 데이터는 Git 밖에 둔다. 저장소에는 고른 문항 ID 목록과 선별 스크립트만 둔다.
  - 문항 분류는 모델이 하고, 사용자는 표본만 확인한다.
- **한국어 서술 답과 사람 라벨** **(결정)**
  - "답"은 서술 문항을 읽고 자기 말로 쓴 설명이다. 객관식·단답은 코드가 채점하므로 사람 라벨이 필요 없다.
  - 답 작성자 **(결정)**
    - 기본: 사용자 혼자 쓴다. 참여 학생은 보수적으로 0명으로 계획한다.
    - 확장: 학생 2~3명이 더 참여할 수 있으면, 답 데이터를 모으는 동안(늦어도 2주차 말) 사용자가 알려 준다.
  - 학생이 참여하면 그 학생의 답을 M3의 중심 데이터로 쓴다 **(Claude 판단)**.
    - 비교 실험의 사전 시험 서술 답과 이해 확인 단계의 서술 답을 쓴다.
    - 사용자 답은 수를 채우는 보조로 둔다.
  - 사용자가 쓴 답의 한계
    - 루브릭을 아는 개발자가 쓴 답이다.
    - 그래서 미통과 답도 일부러 불완전하게 쓴 답이 된다.
    - 모든 답에 "개발자 작성"으로 표시하고, 디펜스에서 이 한계를 먼저 밝힌다.
    - 그래도 Claude가 쓴 가상 답보다는 실제 한국어 답에 가깝다.
  - 답은 스프레드시트나 설문 양식으로 받는다. 시스템 접속은 필요 없다.
  - 목표는 답 150개 이상, 그중 사람 기준 미통과 100개 이상이다.
    - 미통과가 50개뿐이면 거짓 통과가 1개(2%)만 나와도 Wilson 95% 상한이 약 10.5%다.
    - 그러면 "거짓 통과율 10% 이하" 기준을 보일 수 없다.
  - 채점자 **(결정: 석사 과정생 / Claude 판단: 나머지 배치)**
    - 자료구조를 아는 석사 과정생이 모든 답을 채점한다(약 2시간 30분).
    - 사용자는 자기가 쓴 답을 채점하지 않는다.
    - 기본(사용자 혼자 답 작성)일 때
      - 석사 과정생 1명이 채점한다.
      - 사람 대 사람 kappa 대신, 석사 과정생이 2주 뒤 같은 답 50개를 순서를 섞어 다시 채점해 채점자 내 일치도를 낸다.
      - "채점자 1명"이라는 한계를 함께 밝힌다.
    - 확장(학생 참여)일 때: 사용자가 학생 답의 두 번째 채점자를 맡아 사람 대 사람 kappa를 낸다.
  - 채점 규칙
    - AI 판정을 보여 주지 않는다.
    - 두 채점자는 상의하지 않고 각자 채점한다. 같은 채점 기준표와 스프레드시트를 쓴다.
    - 답에는 작성자 이름 대신 번호만 붙인다.
    - 시작 전에 연습용 답 5개로 기준을 맞춘다. 이 5개는 결과에서 뺀다.
  - 최종 라벨
    - 채점자가 2명이면 kappa를 먼저 낸다. 이 값이 AI-사람 일치도의 현실적 상한이다.
    - 판정이 갈린 답만 두 사람이 논의해 최종 라벨을 정한다.
    - 채점자가 1명이면 석사 과정생의 판정이 최종 라벨이다.
    - AI 판정은 최종 라벨과 비교한다.
  - 학생 답이 있으면 결과를 두 가지로 보고한다. 하나는 사용자 답을 포함한 결과, 하나는 제외한 결과다.
- 사람 실험(답 수집, 비교 실험)은 IRB 심의가 필요 없다 **(결정)**.
  - 참여 동의서는 간단히 받는다 **(Claude 판단)**.
  - 학생 답과 실험 기록은 Git 밖에 둔다. 실험이 끝나면 익명화한 수치만 남기고 원문은 지운다 **(Claude 판단)**.
- project-direction의 O4(1주 뒤 재확인)는 장기 학습과 함께 제외한다 **(결정)**. 결과 기준은 O1~O3다.

## 3. 6주 범위와 단계

### 3-1. 범위: B안 (결정)

- 자료구조 36개 개념 전부를 막힘 흐름, 애니메이션, 평가로 증명한다.
- 운영체제는 한 단원만 연결 지도에 붙인다. 다른 과목에도 적용됨을 보이는 증거로 쓴다.
  - 단원은 **CPU 스케줄링**으로 한다 **(Claude 판단)**.
  - 이유 1: 선수 개념이 자료구조의 큐·우선순위 큐·힙으로 이어져 과목 사이 연결을 보여 준다.
  - 이유 2: 간트 차트 애니메이션은 상태를 결정적으로 계산하기 쉽다.
- 나머지 과목(네트워크, 데이터베이스, 컴퓨터개론, 운영체제 나머지)은 6주 뒤로 미룬다.

### 3-2. 진행 방식

| 안 | 내용 | 결과 |
| --- | --- | --- |
| 1안 서비스 기반·장기 학습 먼저 | 4주 기억 측정을 일찍 시작하려고 계정·외부 접속·복습을 앞에 둠 | 처음 채택했다가, 로컬 진행과 장기 학습 제외로 근거가 사라져 폐기 |
| 2안 증명 먼저 | 콘텐츠·애니메이션 → 평가 파이프라인 → 사람 근거 | **채택** **(결정)** |
| 3안 세 갈래 동시 진행 | 콘텐츠·평가·애니메이션을 2주마다 조금씩 | 데이터 PR 검수가 한꺼번에 몰리고 통합 위험이 커서 제외 |

- 스프린트는 1주, MVP는 2주(스프린트 2개) 단위다 **(제안 채택)**.
  - 1주차 스프린트: 구현과 자동 테스트.
  - 2주차 스프린트: 검증, 수정, 운영 반영.
- 매주 진행 발표가 있다. 단계마다 주별로 보여 줄 것을 정해 둔다.
- 남은 기간은 보수적으로 5~6주다. 5주로 끝나면 3-5절의 순서대로 뺀다.

### 3-3. 단계별 구현과 검증

주차 기준: 1주차는 10/26~11/1, 6주차는 11/30~12/6이다.

**MVP 2: 자료구조 콘텐츠 + 애니메이션 (1~2주차)**

- 구현
  1. 자료구조 나머지 25개 개념의 문항을 만든다. 데이터 PR로 나눠 올린다.
  2. 애니메이션 장면 형식과 결정적 상태 계산기를 만든다.
  3. 자료구조 애니메이션: 배열·연결 리스트 포인터, 스택·큐, 해시 테이블, 트리(BST 삽입·삭제, 힙).
  4. 보충(S4)과 채팅에서 애니메이션을 호출한다.
  5. 한국어 답 수집을 시작한다. 지금 있는 서술 문항 11개로, 스프레드시트를 쓴다.
- 검증(완료 기준)
  - 자료구조 36개 개념 전체에서 막힘 흐름이 끝까지 동작한다(E2E).
  - 애니메이션 종류마다 상태 계산이 참조 구현과 일치한다(단위 테스트).
  - 모델의 장면 선택 성공률을 측정한다.
- 주별 발표
  - 1주차: 애니메이션 시연
  - 2주차: 자료구조 전체 흐름

**MVP 3: 평가 파이프라인 (3~4주차)**

- 구현
  1. 시뮬레이션 학습자를 만든다. 서빙과 다른 모델을 GPU 1번에 올리고 약 50회 돌린다(M1, M2).
  2. Mohler 영어 원문으로 개발 검증을 한다(루브릭 작성 포함).
  3. 석사 과정생 채점을 진행한다(기본이면 2주 뒤 재채점 50개 포함).
  4. 비교 실험 모드를 만든다(참가자 ID, 조건 배정, 기록 분리). 2주차 말까지 참여 학생이 확인될 때만 만든다.
  5. 그래프 탐색(BFS·DFS)과 정렬 애니메이션을 추가한다.
  6. 품질 하한 시험(2-4절)을 만든다.
     - KMMLU CS와 CS-Bench에서 자료구조·운영체제 문항을 골라 낸다.
     - CS-300 추적 29개를 실행으로 재검증한다.
     - 서빙 모델(gemma)로 3회 반복하고, 보기만 주는 조건도 1회 돌린다.
  7. (선택) CS-Bench 원문·번역 쌍 비교.
- 검증(완료 기준)
  - 품질 하한 결과: KMMLU 선별분 정답률(수험생 정답률과 나란히), CS-Bench 선별분 정답률, CS-300 추적 60 점수, 보기만 조건 정답률을 각각 3회 평균으로 보고한다.
  - M1 recall ≥ 0.8, 과잉 보충률 ≤ 20%. 미달이어도 수치를 보고한다.
  - Mohler 개발용 일치도와 거짓 통과율.
  - 채점자 간 kappa(채점자 1명이면 채점자 내 일치도).
  - 한국어 답 150개 이상(미통과 100개 이상) 확보.
- 주별 발표
  - 3주차: 시뮬레이션 첫 수치
  - 4주차: 채점 일치도, Mohler 결과

**MVP 4: 사람 근거 + 과목 확장 (5~6주차)**

- 구현
  1. M3 최종값을 계산한다.
  2. 사람 비교 실험을 한다(참여 학생이 있을 때). 제안 시스템과 같은 모델의 일반 채팅을 비교하며(O1~O3), 1인 1회 대면으로 진행한다.
     - 실험 개념은 학생마다 사전 시험에서 처음 보는 개념으로 고른다.
     - 학생이 없으면 O1~O3는 "측정하지 못함"으로 보고한다. 이때 증명은 시뮬레이션(M1, M2)과 M3로 한다.
  3. 운영체제 CPU 스케줄링 단원: 연결 지도 노드, 문항, 간트 차트 애니메이션.
  4. 디펜스 자료를 만들고 문서를 갱신한다.
- 검증(완료 기준)
  - M3 kappa ≥ 0.6, 거짓 통과율 ≤ 10%. Wilson 95% 구간과 함께 보고하고, 미달이면 그대로 보고한다.
  - O1~O3 효과 크기와 사례.
  - 운영체제 단원에서 막힘 흐름이 자료구조 선수 개념(큐·우선순위 큐)까지 내려가 보충한 뒤 복귀한다.
- 주별 발표
  - 5주차: M3 결과, 운영체제 단원 시연
  - 6주차: 최종 수치 종합

### 3-4. 단계 사이 의존 관계

- 한국어 답 수집은 1주차에 시작한다. 교차 채점(MVP 3)과 M3 최종(MVP 4)이 여기에 달려 있다.
- 비교 실험(MVP 4)에는 실험 모드(MVP 3)가 필요하다.
- 시뮬레이션 학습자(MVP 3)가 36개 개념 전체를 돌려면 자료구조 문항(MVP 2)이 병합되어 있어야 한다.
- 자료구조 문항 데이터 PR은 1주차부터 묶음으로 나눠 올린다. 사용자 검수가 한 주에 몰리지 않게 하기 위해서다.

### 3-5. 일정이 밀릴 때 빼는 순서 (Claude 판단)

1. CS-Bench 쌍 비교(선택 항목)
2. 운영체제 단원. 빼면 A안(자료구조만)이 된다.
3. 그래프 탐색·정렬 애니메이션
4. 비교 실험 모드. 빼면 대면 실험을 수작업으로 기록한다.

- 빼지 않는 것: M3 한국어 최종 검증, 시뮬레이션 학습자. 디펜스의 핵심 근거이기 때문이다. 사람 비교 실험은 참여 학생이 있으면 빼지 않는다.

### 3-6. 콘텐츠 규모와 검수 부담 (추정)

| 데이터 | 규모 | 검수 |
| --- | --- | --- |
| 자료구조 나머지 25개 개념 | 개념당 진단 2, 확인 2, 서술 1 + 루브릭 → 약 125문항 | 데이터 PR, 사용자 승인 |
| 운영체제 CPU 스케줄링 | 개념 약 5~6개 × 5 → 약 30문항 | 데이터 PR, 사용자 승인 |
| Mohler 루브릭(영어, 개발용) | 80문항 | Git 밖 보관. 사용자는 표본 20개만 확인 **(Claude 판단)** |
| 사람 실험 사전·사후 문항 | 실험 개념당 A·B형 | 데이터 PR, 사용자 승인. 개념 수는 실험 설계에서 정함 |

- 사용자가 검수할 문항은 실험 문항을 빼고 약 155개다. 주당 약 30~40개 수준이다.
- 검수자 워커가 먼저 정답 독립 계산, CS-300 중복, 형식을 확인한다. 사용자는 내용만 본다.

- 번역한 서술 데이터나 시뮬레이션 결과를 사람 결과처럼 보고하는 경우
- 애니메이션 상태를 모델이 지어내 틀린 그림이 나가는 경우
- 학생 답 원문이나 실험 기록이 Git이나 외부 서비스로 나가는 경우

## 6. 제약

- GPU: RTX 3090 24GB × 2. GPU 0번은 서빙(gemma-4-26B-A4B-it AWQ, `--max-num-seqs 1`), GPU 1번은 시뮬레이션 학습자·실험용이다.
- 새 서비스 포트는 20000 이상을 쓴다. 기존 8000·8001·8080·5173은 유지한다.
- Orca 포트(6768)를 인터넷에 노출하지 않는다.
- 커밋에 넣지 않는 것: 모델 가중치, 가상환경, 비밀정보, 사용자 대화 기록, 학생 답 원문, 생성 결과물.
- PR 규칙: 하나의 목적, 변경 파일 4~5개 이내 목표, main 직접 커밋 금지, `Co-Authored-By` 금지(AGENTS.md, CLAUDE.md).
- 데이터 PR(개념 지도, 문항 은행, 루브릭, 평가 세트)은 사용자가 직접 검수하고 승인해야 병합한다(CLAUDE.md).
- 새 라이브러리(애니메이션 렌더링 등)는 계획 단계에서 목록으로 승인받는다.

- Orca로 진행한다 **(결정)**. 사용자와 이야기하는 코디네이터 1명이 워커에게 일을 나눠 맡긴다.
- 팀 구성은 1차 MVP와 같은 형태로 한다 **(Claude 판단)**.

  - 계층별 워커(AI core, Backend, Frontend)

  - 모델은 claude-opus-5-5, 노력 수준 high
- 이 문서가 승인되면 단계별 구현 계획을 쓰고, 계획 승인 뒤 워커를 투입한다.
